# 阀门智能报价系统：仓库整体治理方案

> 状态：执行中（死代码清理已完成，待进入静态质量分析）  
> 分支：`ykq`  
> 目标：将仓库从“通用 AI Coding 模板 + 阀门报价改造”的混合形态，收敛为边界清晰、可持续演进的阀门业务系统。

## 1. 治理目标

1. **业务聚焦**：产品唯一主线为阀门询价解析、参数归一、产品匹配、确定性 BOM、报价、图纸和黑湖数据协同。
2. **架构清晰**：明确前端、领域 API、纯函数规则、数据访问、外部集成的依赖方向；避免业务逻辑回流到超大页面组件。
3. **安全可控**：多租户必须以可信会话中的 `tenant_id` 为边界；所有 API 写操作可追溯、可验证。
4. **规则可信**：AI 只负责模糊信息提取，产品编码、材质、BOM 和状态流转必须由规则/数据决定并可测试。
5. **可维护交付**：建立最小质量门禁、迁移规范、配置规范和文档入口，降低继续改造的风险。

| 维度 | 当前状态 | 目标状态 |
|---|---|---|

## 2.1 执行总顺序（当前共识）

治理遵循“先减负、再体检、后加固”的顺序，避免在死代码和模板遗留上投入优化成本：

1. **剔除死代码**：先移除 AI Coding/Sandbox 遗留、无入口页面、无消费者组件和仅为这些能力存在的依赖；每个删除批次独立提交、可回滚。
2. **静态质量分析**：对保留代码依次执行 React Doctor、TypeScript 类型检查、lint、规则单测和生产构建。优先修复安全性、正确性、性能和阻断构建的问题，建立健康基线。
3. **模块划分治理**：在健康基线上按报价、参数与产品、BOM 规则、图纸、黑湖、租户与认证等功能域拆分；每次只迁移一个模块，并保持静态检查持续通过。
4. **业务稳定性治理**：模块边界稳定后，重点验证数据库迁移与备份、Supabase RLS、多租户隔离、登录会话、权限边界、报价主链路、Kimi 降级和黑湖同步一致性。
5. **持续门禁**：把稳定后的静态检查和关键业务回归放入 CI，防止后续改造重新引入问题。

## 3. 目标架构与边界

```text
浏览器（阀门报价工作台）
  → Next.js Route Handlers（认证、输入校验、领域编排）
    → lib 领域规则（归一化、匹配、BOM、高温、状态机）
    → Supabase（多租户 PostgreSQL / Storage）
    → 外部服务（Kimi、黑湖）
```

### 保留的核心域

- 报价：`quotes`、`quote_items`、报价状态、打印与项目视图。
- 参数与产品：参数词典、19 位编码、归一化、产品匹配、历史命中。
- BOM 与规则：牌 1/牌 2、模板、小样图骨架、高温规则、确定性合成。
- 图纸：上传、解析、预览、字段填充和 Storage 管理。
- 黑湖：订单、客户、产品、物料、库存、全量/增量同步与齐套分析。
- AI：Kimi 文本/视觉参数提取与必要的数据初始化辅助；输出必须进入规则校验。

### 明确不再承载的能力

- 面向最终用户的通用 AI 编程助手。
- Vercel Sandbox 中的建项目、写文件、执行命令、实时预览。
- 通用 Coding Agent 的多模型选择、命令日志、文件浏览器、错误自动修复。

## 5. 分阶段实施路线

### Phase 0：基线冻结与决策

- 明确目标用户、租户模型、报价单生命周期、黑湖职责边界。
- 备份生产 Supabase 数据与 Storage；记录当前环境变量、迁移版本、部署地址。
- 在删除前执行现有规则测试、类型检查和生产构建，保存基线结果。

### Phase 1：产品与代码收敛

- 按第 4 节 A → D 批次移除 AI Coding 遗留，每批单独提交并执行 `pnpm type-check`、测试、构建。
- 将 `/api/claude` 改名为业务语义 API（迁移期保留兼容路由或同步改前端调用）。
- 重写 README、应用 metadata、欢迎文案与环境变量样例。

### Phase 2：前端领域化

- 将 `components/valve-quote/app.tsx` 拆分为 `features/quotes`、`features/products`、`features/rules`、`features/drawings`、`features/kitting`。
- 提取请求 hooks、领域类型、表单状态和展示组件；页面层只负责组合。
- 为客户端 DTO 与 API 入参建立共享 schema，减少隐式中文字段协议漂移。

### Phase 3：API、鉴权与数据治理

- 所有写 API 使用 Zod schema 校验、统一错误码与审计字段。
- 审核 Supabase RLS，确保任何表/Storage 操作都按 `tenant_id` 隔离；不要仅依赖客户端传参。
- 明确会话失效、租户停用、管理员权限与密码策略；生产环境禁止默认密钥。
- 为数据库迁移建立“可前滚、可验证、禁止手改生产库”的流程。

### Phase 4：规则与 AI 质量治理

- 规则集增加版本号、生效时间、租户范围、变更人和回滚能力。
- 建立典型询价、边界 DN/压力/材质、高温和历史 BOM 的回归样本集。
- AI 输出先做 JSON/schema 校验，再经归一与规则校验；记录置信度、待确认项与人工修正。
- 用事件表沉淀“输入 → 建议 → 人工确认 → 成交/失单”的闭环，但避免把未经审核的 AI 输出直接当规则。

### Phase 5：工程与运行治理

- CI 最低门禁：类型检查、规则单测、构建、迁移静态检查。
- 观测：API 错误、Kimi 调用成功率/耗时、黑湖同步水位、BOM 规则命中/回退率。
- 运维：环境变量清单、密钥轮换、备份恢复演练、发布与回滚手册。
- 文档：架构说明、数据字典、规则编写指南、黑湖映射说明、业务员操作手册。

## 6. 质量门禁与验收标准

每一阶段完成前至少满足：

1. `pnpm type-check` 通过。
2. `lib/*.test.mjs` 中规则测试通过；新增规则必须新增正反例。
3. `pnpm build` 通过，且首页可加载报价工作台。
4. 新建报价主链路可验证：询价输入 → 参数提取 → 归一/确认 → BOM → 保存 → 打印。
5. 两个不同租户不能读取或写入对方的报价、规则、图纸与同步数据。
6. 黑湖增量同步可重复执行，水位推进与失败重试可观察。

## 7. 推荐提交策略

- 一个提交只做一个可回滚主题：例如“移除 Sandbox API”“移除 Coding UI”“替换 README”。
- 删除前后都执行检查；不要把代码清理、规则重构和数据库迁移混在同一提交。
- 任何数据结构变更必须先提供迁移，再改应用代码，最后清理兼容代码。
