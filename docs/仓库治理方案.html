阀门智能报价系统
仓库整体治理方案

将“通用 AI Coding 模板 + 阀门改造”的混合仓库，收敛为边界清晰、规则可信、可持续演进的阀门业务系统。

治理主张：产品只服务阀门问题。保留 Kimi 的阀门文本/图纸解析能力，但删除“创建应用、写文件、执行命令、Sandbox 预览”的通用 AI 编程平台遗留。

目标状态

业务聚焦

询价解析、参数归一、产品匹配、确定性 BOM、报价、图纸与黑湖协同构成唯一主线。

规则可信

AI 负责模糊提取；编码、材质、BOM、状态流转均由规则和数据决定，并可测试与审计。

租户安全

可信会话中的 tenant_id 是所有数据访问边界，配合数据库 RLS 与 API 校验。

治理路线图

第一步

剔除死代码

先移除 AI Coding、Sandbox、无入口页面和无消费者组件；删除批次独立、可回滚。

第二步

静态质量体检

对保留代码运行 React Doctor、TypeScript、lint、规则单测和生产构建。

第三步

模块划分治理

按报价、参数与产品、BOM 规则、图纸、黑湖、租户与认证等功能域拆分；每次只迁移一个模块。

第四步

解决关键问题

优先处理安全、正确性、性能和构建阻断；一般风格问题不抢占业务稳定性投入。

第五步

业务稳定性

集中治理数据库、迁移与备份、RLS、多租户、登录会话、Kimi 降级和黑湖同步。

第六步

持续门禁

将静态检查和关键业务回归纳入 CI，防止后续改造重新引入问题。

静态分析的处理优先级

分析工具链

  1. React Doctor：React 正确性、性能与安全类诊断。
  2. pnpm type-check：类型边界、空值与接口协议。
  3. Lint：React Hooks、可疑写法、未使用代码与基础规范。
  4. 规则单测 + pnpm build：BOM 领域回归与交付可用性。

修复排序

  1. 安全和跨租户数据泄漏风险。
  2. 构建失败、运行崩溃、错误业务结果。
  3. 严重性能退化与报价主链路阻塞。
  4. 可维护性、风格和非阻断提示。

关键治理动作

前端与 API

  • 将 ValveQuoteApp 分拆成报价、产品、规则、图纸、齐套 feature。
  • API 统一使用 Zod 校验、稳定错误码和审计字段。
  • 客户端 DTO 与接口入参共享 schema，减少字段协议漂移。

数据与权限

  • 按 tenant_id 审核所有表和 Storage 的 RLS 策略。
  • 生产环境禁用默认认证密钥与空密码进入。
  • 迁移必须可前滚、可验证；禁止直接手改生产库。

规则与 AI

  • 规则集支持版本、生效时间、租户范围、变更人和回滚。
  • AI 输出先过 JSON/schema，再进入归一化与确定性规则。
  • 沉淀询价→建议→人工确认→成交的回归样本闭环。

运行与交付

  • 最小 CI：类型检查、规则测试、构建、迁移静态检查。
  • 监控 Kimi 成功率、黑湖水位、BOM 回退率和 API 错误。
  • 维护备份恢复、发布回滚、数据字典、规则指南与操作手册。
