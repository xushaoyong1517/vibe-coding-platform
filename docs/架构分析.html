阀门智能报价系统：整体架构分析

基于当前代码库（2026-07-11）的静态分析。通用 AI Coding 与 Sandbox 遗留已剔除，仓库已收敛到阀门业务主线。

Next.js 16单仓全栈 BFF
Supabase多租户业务数据
Kimi非确定性信息提取
纯函数规则确定性 BOM 合成
一句话结论：浏览器中的 React 单页报价工作台通过 Next.js Route Handlers 调用 Kimi、规则引擎和 Supabase；AI 仅负责把询价文本/图片转为结构化参数，材料与 BOM 由可测试的确定性规则生成。

关键设计：AI 与规则分工

AI：处理不规范的自然语言、表格、图片，抽取候选参数。
规则：归一化、产品匹配、牌号材质、高温升级和 BOM 填充。这将高风险、可验证的业务知识从 LLM 输出中剥离出来。

BOM 的三级回退

  1. 相近编码、结构和驱动条件的历史报价骨架
  2. 关联小样图模板（兼容占位符旧模板）
  3. 标准 15 行的 deriveBOM 结果

无论骨架来源，材质仍以当前租户规则重新填充，避免复制历史错误。

多租户的关键入口是 getTenantId(req)：优先读取签名 Cookie 中的 tenant_id，API 再以该值写入和过滤数据。认证采用 HMAC 签名会话 + scrypt 密码哈希；生产环境会拒绝默认密钥。

5. 外部能力与运行时

黑湖同步

runSync 统一服务于手动接口和定时任务。增量同步读取上次水位，额外回看 15 分钟抵消边界漏数；批量 upsert，每日/全量模式再清除本次未刷新的陈旧数据。

Kimi 领域 AI

/api/claude 和图纸解析接口调用 Moonshot 文本/视觉模型，处理非结构化输入；材料、编码与 BOM 仍由领域规则决定。

6. 架构判断与优先级建议

优势

  • “AI 提取 + 规则决策”的边界正确且可审计。
  • 规则函数配有多份 *.test.mjs，适合持续固化制造知识。
  • 历史 BOM 只复用零件骨架、重算材质，降低经验污染。

主要风险

  • ValveQuoteApp 职责过多、文件很大，领域状态与视图耦合。
  • 当前仍有一处 TypeScript 类型错误，生产构建基线尚未完全通过。
  • 数据客户端使用 Supabase anon key；生产安全高度依赖 RLS 与 API 层租户过滤。

建议演进顺序

  1. 完成 React Doctor、TypeScript、lint 与构建基线。
  2. 将报价工作台按“报价/规则/数据/齐套”拆为 feature 模块与 hooks。
  3. 为每个 API 建立输入 schema 与鉴权/tenant 测试。
